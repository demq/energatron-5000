# Contributing to energatron-5000

Thanks for helping. This tool handles people's energy data, so the first rule comes before everything else.

## Never share your own data

- Don't attach meter downloads, bills, usage exports, recommendations or screenshots of them to an issue or a pull
  request. Don't paste an NMI, a meter serial, an account or invoice number, a MIRN, an address, a postcode, or kWh or
  dollar figures from your own household.
- For a bug report, run `uv run energatron diagnose --json` in your workspace, read what it prints (it holds versions,
  structure and error codes, never values), and paste that.
- If a bug needs a file to reproduce, describe its structure (columns, record types, what's unusual) and we'll write a
  synthetic one.

## Set up

You need [uv](https://docs.astral.sh/uv/) and git. Python 3.14 and every tool come through uv; nothing is installed
globally.

```bash
git clone https://github.com/demq/energatron-5000
cd energatron-5000
uv sync
uv run pre-commit install
```

## The checks (all must pass)

```bash
uv run ruff check
uv run ruff format --check
uv run pyright
uv run lint-imports
uv run pytest -q
uv run pre-commit run --files <changed files>
```

CI runs the same, the privacy guard over every tracked file, and the demo end to end on macOS.

## How the code is organised

- Read `agent_docs/2026-10/2026-10-23_core-architecture-spec.md` (D1) before changing code; it is binding.
- Layers point down: `adapters → services → ports → core`. Core does no I/O; services touch only files at paths they
  are given; git, DVC and other subprocesses live in adapters. `lint-imports` enforces this.
- Every persisted document has `kind` and `schema_version`. Changing a model bumps its version and adds a migration in
  core, plus a golden document in `tests/fixtures/schemas/<kind>/`.
- Every command supports `--json`; errors use the codes in `core/errors.py`. From version 0.1 on, renaming a command,
  an option or a JSON field needs a release that deprecates the old name first.
- Write tests first. Test fixtures are synthetic and generated by code (`tests/fixtures/`), never derived from real
  files.
- If you change `scripts/privacy_guard.py` or `scripts/check_agent_links.py`, copy it to
  `src/energatron/templates/workspace/dot-energatron/scripts/<name>.tmpl` (a test checks they match) and bump
  `TEMPLATE_VERSION` in `core/workspace_template.py`, so `energatron upgrade` brings it to existing workspaces.

## Adding a region

A region is a profile in `src/energatron/regions/<name>.yaml`; South Australia (`sa.yaml`) is the example. It holds:

- `local_tz`: the IANA time zone of the network (it must be in `tzdata`).
- `tou_windows`: the time-of-use windows retailers use on that network, which must cover every minute of the day once.
- `distributor` and `gas_distributor`: the network names exactly as the Consumer Data Right (CDR) plan APIs print them
  in `geography.distributors`.
- `cdr_retailers`: the CDR base URIs of the retailers selling on that network, from the AER's published list.
- `parsers`: the source types that region's files come in.

NEM12 is the national meter-data format, so downloads from other distributors should mostly parse; a distributor whose
file names or summaries differ needs a parser change and a synthetic fixture that shows the difference.
`tests/architecture/test_region_profiles.py` must pass for the new profile. A region pull request holds no real data:
check the names and URIs against the public CDR APIs, not against your bills.

## Adding or changing a parser

Parsers live in `src/energatron/adapters/sources/`, one per source type, registered in `registry.py`. Add a synthetic
generator for the format to `tests/fixtures/`, test what the parser accepts and rejects, and bump the parser's
`version` when its output changes.

## Changes, commits and releases

- Add a line under `## [Unreleased]` in `CHANGELOG.md` for anything a user would notice.
- Commit messages say what changed and why, without figures or identifiers. Never use `--no-verify`.
- Releases follow [Semantic Versioning](https://semver.org/). To cut one, a maintainer sets `version` in
  `pyproject.toml`, renames `[Unreleased]` in `CHANGELOG.md` to the version and date, commits, and pushes a tag
  `v<version>`. The release workflow checks that the tag matches the version, runs the checks, builds the wheel and the
  source archive, and publishes a GitHub release with the changelog section. There is no PyPI package yet.
